==================================================
1) Product Direction (Updated)
==================================================

VaaniAI is now implemented as a web-interactive voice receptionist backend.
Telephony/call routing is not required for current delivery.

Core objective:
- patient speaks in browser UI,
- backend transcribes speech,
- assistant handles booking or inquiry conversation,
- booking is confirmed only after verbal data collection and screen review,
- confirmation SMS is sent to patient phone.

Emergency workflow is intentionally excluded for now.

Current delivery target:
- demo MVP, not production deployment,
- web voice-agent UI instead of telephone call routing,
- local, tunneled, and hosted testing with real provider keys.

Backend completion estimate for this agreed MVP:
- 98-99% complete before final hosting setup and live provider sign-off.

3) Booking Conversation Contract
==================================================

Implemented conversation flow:

1. User asks by symptom or specialization.
   Example: "I have chest pain" -> mapped to cardiologist intent.
   Example: "I need an orthopedics doctor" -> mapped directly to orthopedics.

2. Backend returns slot options (`slot_options` in chat response).
   The frontend keeps these options visible until the user selects a doctor/slot.

3. User chooses slot (time text or slot id).
   The frontend then shows a selected appointment panel with doctor, specialty, slot, and time.

4. Backend collects patient details in strict order:
   - name
   - gender
   - age
   - phone

5. Backend returns `booking_review` payload for on-screen confirmation.
   The frontend keeps the review panel visible until the user confirms or denies/corrects.

6. User says confirm.
   - appointment is created,
   - slot is locked,
   - confirmation SMS is sent via configured provider,
   - chat returns `next_state=booked` with booking id and notification status.

If user says no at review stage, backend loops back to re-collect details.

==================================================
4) Voice Interaction Modes
==================================================

Mode A: Step-by-step integration
- frontend uploads audio to `/transcribe`
- frontend sends recognized text to `/chat`
- frontend calls `/tts` for assistant speech

Mode B: Single-turn orchestration (recommended)
- frontend uploads audio to `/voice/turn`
- backend performs STT -> chat -> optional TTS in one request
- response contains:
  - `stt_text`, `stt_status`
  - `chat` (reply, state, actions, slot options, booking review)
  - `tts` (audio url/status) when synthesis enabled

5) Providers and Environment
==================================================

Configured target stack:
- STT: ElevenLabs
- TTS: ElevenLabs
- Optional speech-to-speech: ElevenLabs
- LLM fallback/inquiry: OpenRouter

9) Handoff for Frontend
==================================================

Frontend can be built now directly against these stable contracts:
- `/app` to open the current web voice UI
- `/session/start` to initialize a new interaction id
- `/voice/turn` for main voice loop
- `/session/{call_id}` to rehydrate current state if page reloads
- `/chat` as text fallback
- `/notifications` for delivery audit/debug

Recommended frontend flow:
1. Create or reuse a `call_id`.
2. Start session with `/session/start`.
3. Vaani speaks: "Hi, I am Vaani from Pawani Medicals. Tell me what is going on, and I will help you find the right appointment."
4. Browser listens automatically and records until silence is detected.
5. Recorded audio is sent to `/voice/turn`.
6. Backend returns STT text and chat response.
7. Browser speaks returned `chat.reply` or backend TTS audio when available.
8. Render `chat.slot_options` as doctor/slot cards when present. Vaani should summarize these naturally instead of reading every slot aloud.
9. Keep slot cards visible until selection; after selection, show the selected appointment panel.
10. Render and preserve `chat.booking_review` before final confirmation.
11. On `next_state=booked`, show green success tick and booking id.
12. Use `notification_status` to show whether Fast2SMS confirmation was sent/logged.
13. After the confirmation moment, clear visible booking details and start a fresh idle session automatically.

Live MVP test path:
- `mic audio -> /voice/turn -> ElevenLabs STT -> booking state machine/OpenRouter fallback -> ElevenLabs TTS -> appointment DB save -> Fast2SMS SMS -> frontend success state`

Current frontend status:
- implemented as static files in `frontend/`
- served by FastAPI at `http://127.0.0.1:8000/app`
- uses automatic microphone recording with silence detection for `/voice/turn`
- uses browser speech recognition only for interim transcript when supported
- uses backend TTS audio when available, otherwise browser speech synthesis for Vaani's spoken replies
- hides patient-facing transcript while preserving backend transcript logs
- includes typed fallback through `/chat` with Enter key only when microphone access is blocked
- no visible buttons in the main interaction

10) Hosting Readiness
==================================================

Hosting is the next major step after final local provider testing.

Required host configuration:
- set `PUBLIC_BASE_URL` to the hosted HTTPS URL,
- set `DATABASE_URL` to the selected hosted database,
- configure ElevenLabs, OpenRouter, and Fast2SMS secrets,
- keep generated audio and secret JSON files out of git,
- enable Google Calendar only when credentials and calendar sharing are ready.

Temporary public sharing:
- run locally on a non-blocked port such as 8020,
- use `ngrok http 8020`,
- share `https://<ngrok-domain>/app`.
